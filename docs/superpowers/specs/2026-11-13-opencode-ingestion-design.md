# OpenCode conversation ingestion (issue #12)

Status: proposed design; public-source audit completed, human approval pending.
No product implementation or OpenCode compatibility claim accompanies this document.

## Intent and scope

SelfOS should extract lasting knowledge from local OpenCode conversations with the same one-click workflow used for Claude Code and Codex. Preserve project context, provenance, backups, corrections and resume behavior; do not ask a model to classify the same conversation twice. Also accept OpenCode exported JSON through the document-import admission boundary being developed under #11. OpenCode support is a deliverable within #12, not proof that the entire issue is resolved: the exact DeepSeek Harness distribution remains unidentified.

No upstream execution, paid model calls, or personal conversation access during development. Verification uses synthetic fixtures and injected summarizer/refiner callbacks. Product model calls continue through existing configured providers.

## Approaches

The implementer proposes native read-only SQLite plus exported JSON adapters sharing normalization and evidence resolution. This meets automatic local discovery and portable file ingestion. Export-only ingestion is simpler but misses one-click local discovery and depends entirely on #11. Invoking the OpenCode CLI uses its projection but may initialize/migrate upstream storage and provides poor control over bounded reads and cancellation. The CLI is not invoked. The selected approach is an implementer recommendation, not recorded user approval.

Record the profile identifier in source metadata. Advertise the verified profile rather than all OpenCode releases. More profiles require pinned evidence and independent fixtures.

## Adapter and record contract

Add an adapter interface owned by `selfos.sources`: discovery, bounded scan, normalized messages and original-message resolution. Preserve the existing Claude/Codex behavior behind its current reader. The OpenCode module owns SQL and export parsing; the knowledge pipeline consumes normalized messages, not storage-specific branches.

Normalized messages retain existing `id`, `source`, `role`, `timestamp`, `text`, `project`, `project_id`, `session_id`, `path` and `provenance`. Set source to `opencode`. Project identity uses canonical directory when present, matching existing cross-Harness project grouping; native upstream project id remains additional metadata. When no directory is available, use a namespaced native project identity and a neutral display label. Keep `cwd` separately for project exclusions; never resolve opaque ids as filesystem paths.

Store a versioned `source_locator` with profile, origin kind (database or admitted document), native project/session/message identifiers, ordered included part ids and a content digest. Database origin stores a canonical allowed database path. Document origin stores the admitted immutable original path and its hash/filename. Do not accept arbitrary nested metadata from a model. Locator validation is application-owned and occurs before generation and publication.

Provenance is explicit before identity/deduplication. For native database messages, call existing content_identity after text normalization: user_statement/assistant_suggestion remain subject to its quoted/runtime recognition. Exported transcript records use quoted_dialogue for both roles, matching existing document-import evidence rules; an uploaded role=user is not proof of a direct personal statement. No automatic trust promotion, including when a database copy also exists. Preserve both transport role and content provenance in model payloads and source metadata. Exports may support attributed project/history context under current record validation but cannot alone establish a direct personal fact/preference.

Logical message identity hashes a namespace, native project/session/message ids, normalized project directory, UTC creation timestamp, role, normalized provenance and digest of meaningful text. Database path and export filename are not part of logical identity. Copies with identical semantic metadata and text deduplicate; different message ids remain distinct even when text/timestamp match. Differences in project/time/provenance/text produce distinct evidence identities and a metadata-conflict diagnostic for the same native key. Database and export copies with different trust provenance remain distinct; do not suppress either or combine trust. No preferred-locator switch can change project/time/role/provenance. Missing required native ids/time/project linkage is diagnosed and rejected, not filled from another copy. Modified evidence does not silently overwrite existing knowledge. Exact identical copies may provide multiple locators; maintain a bounded deduplicated locator list (maximum 8) and a diagnostic for excess copies. Prefer a permitted verified locator, never an excluded alternate. Existing single-path fields remain compatibility views of the preferred locator. All locators survive staging/cache replay, backup and migration.

Keep only explicit user/assistant text parts with ignored and synthetic flags not true. Exclude reasoning, tool payloads, file contents, environment instructions and assistant compaction summaries. Apply existing redaction and meaningful-request filtering. Join included parts in native part-id order with a newline. Preserve that order in export parsing regardless of file array order; reject duplicate/conflicting native ids within a source. UTC timestamps derive from validated finite nonnegative epoch milliseconds; no invented current timestamp. Invalid role/id/time/type is diagnosed and skipped, not repaired by a model. Unrecognized nontext parts are counted as filtered.

## Discovery, selection and privacy

Discovery never reads transcript bodies. Compute XDG_DATA_HOME (absolute only) or home/.local/share, append opencode, and discover the default opencode.db. Honor an explicit OPENCODE_DB filename under that data root or an absolute filename; :memory: is reported unavailable. Do not infer data paths from OPENCODE_CONFIG_DIR or OPENCODE_TEST_HOME. Nondefault channel databases can be selected explicitly; avoid recursively searching the user's home or launching OpenCode.

Extend source settings with typed entries while preserving version-1 configured roots/exclusions exactly. Version-1 roots become directory entries; OpenCode is offered as available discovery and added only when the user enables it. For fresh defaults, include the discovered standard OpenCode entry in the same visible source setup as Claude/Codex. Database entries identify exact files; directory entries continue supporting current JSONL behavior. Do not silently broaden previously saved permissions.

Separate storage-file exclusions from project-directory exclusions. For OpenCode, query session metadata first; excluded project sessions must never load message/part bodies or enter model payloads. Recheck source permissions against every selected locator immediately before model requests, refinement and canonical publication using the existing policy lock/hash boundary. Apply the same rules during source viewing and migration. A record is eligible when at least one fully permitted locator is available; filtered output includes only permitted locators. Synthetic tests cover a database outside the excluded project directory that nevertheless contains that project's sessions.

## Read-only snapshots and bounds

Open SQLite with URI mode=ro, query_only enabled, trusted_schema disabled where supported, extension loading disabled, parameterized SQL and a bounded busy timeout. Never use immutable=1 for live WAL storage; never copy only the main database file, checkpoint it, or apply migrations. Ordinary read-only SQLite may use existing WAL/SHM coordination; never promise byte-for-byte immutability of coordination files. Persisted upstream database content and schema must not change. If filesystem access cannot support a consistent read-only WAL read, report unavailable and offer export import.

Use one bounded read transaction for a scan snapshot; fetch only required columns and page by validated creation timestamp/native id. Check cancellation before each session/page and install a progress handler with a monotonic deadline. Close connections/transactions in finally. Builder chooses exact conservative defaults, documented/configured before release: session/page/part/record byte caps, total run snapshot deadline and item budget. Bound SQL text/JSON size with length predicates before returning rows. A single oversize message/part is diagnosed and skipped, not truncated into a falsely complete source.

When caps are reached, report partial scan and a resumable scan cursor tied to schema profile and ordered snapshot high-water mark. Never label a bounded sample as the entire history. An explicit later continuation reads remaining eligible records; interrupted scans do not mark unread sessions completed. Do not pass the next page as a fresh session starting at part zero. Introduce a durable scan/compaction checkpoint in SelfOS-owned staging: validated scan profile/high-water mark, native page cursor, stable next compact-part ordinal, included message identities/digests and the last unsealed compact part. Publish each scan-page checkpoint plus its normalized redacted input atomically before advancing its durable cursor. RunJournal is display-only and never proves completion.

Share the existing compaction policy through a resumable compaction primitive: deterministic native message order and fragment offsets, stable monotonically increasing part ordinals within a session snapshot, and the same character packing/filtering as a full scan. Only sealed parts enter summarization; the last unsealed part carries across scan pages and seals when the snapshot session ends. A stop preserves the unsealed part. Scan caps may withhold that last part with an explicit pending notice; they never summarize it under an ordinal that a later page repurposes. Preserve current non-OpenCode prepare_sessions behavior and cache keys. Canonical publication includes the corresponding processed-part and scan checkpoint state in the existing transaction; staged page progress may be ahead of canonical publication only if its sealed parts are still explicitly pending. Recovery queues those pending parts before any later cursor progress.

Disk and memory staging both have documented caps; if a checkpoint cannot be atomically saved, stop without advancing the cursor. A restart/rebuild revalidates processed message digests and profile. A changed prefix invalidates that snapshot's staged continuation with restart instructions; do not combine fragments from different snapshots or silently retain conflicting summaries. Existing canonical work remains until a successful explicit rebuild. New records beyond the captured high-water mark belong to a later scan. Do not rely on SQLite rowid for message identity or stable resume.

Export parsing is limited to admitted UTF-8 immutable originals under #11, with the existing 20 MiB cap, strict expected top-level shape and bounded message/part counts. Do not scan every arbitrary JSON file in selected folders as a conversation. A sanitized export is not distinguishable reliably from ordinary placeholder text: show this limitation in help and allow existing meaningful-content filtering; never reconstruct redacted content.

## Pipeline, resume and evidence

Normalized messages enter existing compaction, policy, summarizer, corrections, cache fingerprints, request usage and transaction publication. No second LLM extraction stage. Before generation/publication, validate semantic metadata and content digest in a fresh bounded source snapshot. At least one permitted locator for each evidence identity must verify; changed/missing/denied alternate copies are excluded with diagnostics, and a matching stable copy may be used. If none verifies, preserve saved work and report source-changed/unavailable with restart instructions. Do not hash the entire mutable database as evidence. Cache-only refinement must validate supported locators and current privacy as well.

The guarantee is validity in the final verification snapshot, with its local verification timestamp, not a lock on external OpenCode writes through canonical publication. SelfOS cannot prevent a Harness modifying its database immediately afterward. Original viewing always rechecks and reports changed content rather than asserting current equality based on the earlier verification timestamp. Snapshot-continuation integrity is stricter: a changed already-consumed prefix invalidates that scan checkpoint even if unrelated canonical records have other valid copies.

Original-source viewing resolves native session/message/part identifiers in a fresh bounded read-only transaction or the immutable exported document, recomputes the same normalization/digest and then uses existing source pagination. Return source_missing, source_changed, source_denied, unsupported_source_format or bounded-read status explicitly. A forged id pointing at another project must fail the session/project linkage checks. Never replay unrelated tool traces. Legacy JSONL/document source handlers and links remain supported.

Locator lists and typed selection participate in migration validation. Migration cannot grant permission to remote paths or trust an arbitrary database locator from a bundle; imported locators remain unavailable until a local source entry is selected and verified. Preserve hash-protected document originals through #11 admission/migration.

## UI and delivery boundaries

Use existing source setup/settings with English default and locale resources. Show OpenCode location, enabled state, available/unsupported/locked status, scanned/filtered/skipped counts and partial-scan notices. Existing progress and stop controls remain the sole organizer controls. Source details show Harness name and original reference, with the existing source viewer. No new page or API bypassing authentication.

Deliver in dependency order: normalized locator/selection boundaries; native adapter and source resolution; export adapter connected to #11 admission; pipeline/cache/privacy/migration and localized UI integration; end-to-end acceptance. These are internal steps, not separate narrower success definitions. Keep #12 open until all named Harness requirements are satisfied; do not close #11 for parser-only work.

The export parser depends on a separately approved and delivered #11 admission/registry design; this document does not authorize inventing its upload endpoint/UI. Required handoff contract: application-validated immutable original under `.knowledge_uploads/originals`, UTF-8 bytes up to 20 MiB, verified SHA256, original filename and stable admitted-document identity; dispatch explicitly to the OpenCode-export adapter only after strict shape validation. Unregistered filesystem paths and arbitrary request-supplied locator metadata are rejected. Until #11 ships that contract, test export normalization with synthetic admitted documents through an internal adapter fixture but do not advertise user-facing export import or call the complete OpenCode deliverable finished. Native adapter work can proceed independently after this design is approved. Full #12 delivery still requires the connected export path and exact DeepSeek integration.

Incremental Harness roadmap: first OpenCode as the pinned reference adapter; second the exact user-identified DeepSeek Harness with its own pinned format audit; then investigate Cline/Roo Code and Aider as candidates for editor-based and terminal-based workflows. These are candidate investigations, not popularity rankings or support promises. For every candidate, first verify project/distribution, supported release, storage/export availability, provenance and licensing of fixture samples. Prefer formats with stable native identities and bounded local reads. Reuse the adapter contract and only advertise a Harness after its fixture and integration gates pass.

## Verification and builder decisions

Tests use synthetic SQLite/export records only. Cover read-only committed WAL visibility without persisted DB/schema mutation; unsupported/V2-only schemas; role/text filtering; same-time ordering; multiple projects/sessions; duplicate/conflicting ids; database/export copy dedup and altered originals; oversize/corrupt records; injected locks/deadlines/cancellation; scan cap continuation; source linkage attacks; privacy before content reads and all model dispatch; cached refinement provenance; backups/recovery; portable import validation; existing Claude/Codex compatibility; authenticated routes; English/Chinese UI and bounded sampling. Inject model callbacks and assert dispatch counts. Run relevant tests, full regression and isolated browser integration. No physical Mac compatibility claim from synthetic path tests.

The builder chooses module names, small helper decomposition, conservative documented resource defaults, and internal cursor serialization without changing the invariants above. Unknown earliest supported historical release and DeepSeek distribution remain explicit research requirements; do not guess them.
